# 試験手順書 整形スキル（test-procedure-formatter）

社内の「試験手順ランナー」Webアプリ（`TestRunner` / `TestRunner/en`）に読み込ませるため、
**与えられた試験項目を Test Runner の Markdown 形式へ整形する**スキル。
手順書を新規に書き起こす用途は持たない（内容を考えるのは依頼者の仕事で、
このスキルの仕事は書式を合わせることだけ）。

このアプリのパーサーは書式に細かいルールがあり、ルールを外すと**エラーにはならず、
その項目が黙って消える**。このスキルは実際のパーサーをそのまま同梱し、
整形した手順書を検証してから納品する。

**このディレクトリは配布物。** `/TestRunner/skill.zip` からダウンロードして展開すると
`test-procedure-formatter/` フォルダができる。それを別端末の `.claude/skills/` の下に
置けば、その端末に元のリポジトリが無くてもそのまま動く（`parser.js` は依存ゼロの
1ファイルで、外部の import を持たない。zip はリクエストのたびにアプリ本体の
`parser.js` を詰めて組み立てられるため、ここに入っている `parser.js` が
本体より古くなることはない）。

## 作業手順

1. `format.ja.md`（日本語に整形する場合）または `format.en.md`（英語の場合）を読み、
   そこに書かれている書式に厳密に従って、与えられた試験項目を Markdown に整形する。
   - 見出しキーワード（`用語定義:` / `Glossary:`、`配布物:` / `Attachments:`、
     `ビルド:` / `Build:` など）、区切り記号（`…`）、表の列見出し、節見出しの
     `【】`/`[]` タグは**すべてこのアプリのパーサーが機械的に読む構造**。
     文面を変えるのは自由だが、この構造マーカー自体は変えないこと。
   - **内容の追加・削除・解釈の変更はしない。** 不明な点は推測で埋めず、
     そのまま残す。試験項目を新しく考え出すことはしない。
2. 整形した Markdown をファイルに保存し、**必ず**次を実行する:
   ```
   node validate.mjs <保存したファイル.md> --lang ja   # 日本語の場合
   node validate.mjs <保存したファイル.md> --lang en   # 英語の場合
   ```
   （node が PATH に無い環境では絶対パスで呼ぶ。例:
   `"C:\Program Files\nodejs\node.exe" validate.mjs <file> --lang ja`）
3. 出力を読み、警告が1件でもあれば整形をやり直してから再実行する。
   **警告ゼロになるまで納品しない。**
   - **終了コードで判定できる。** error 級または warn 級が1件でもあれば `1`、
     警告なし（または info 級のみ）なら `0` が返る。
     warn 級は「元にあった項目が黙って落ちている」状態なので、必ず直すこと。
   - `glossary-duplicate-key` / `materials-duplicate-key` /
     `material-no-url` / `duplicate-item-number` は info 相当（下記参照）で、
     終了コードには影響しない。元の項目にも同じ重複があるなら残してよいが、
     整形の過程で紛れ込んだ重複なら直すこと。
4. 「✅ 試験項目: N件 / M節」の N（拾えた項目数）が、元の試験項目の数と
   一致しているか目視で確認する。**警告が出ていなくても、元と数が変わっていないか
   は別途自分の目で数える**（このアプリの設計上、書式ミスは警告として拾えるものが
   多いが、全ての「意図と違う」パターンを警告化できているわけではない）。
5. 機械可読な結果が欲しい場合（別ツールに渡す等）は `--json` を付ける:
   ```
   node validate.mjs <file> --lang ja --json
   ```
   `{ ok, summary, warnings }` が返る。`ok` は終了コードと同じ判定
   （`totalItems > 0` かつ error 級・warn 級の警告が無い）。info 級は影響しない。

## 警告の読み方（kind ごと）

| kind | 意味 | 直し方 |
|---|---|---|
| `no-items`（error） | 試験項目が1件も読み取れなかった | 表の書式（`\| 列 \| 列 \| 列 \|`、見出し行＋区切り行＋データ行）を見直す |
| `section-without-table`（warn） | 番号付き節見出し（`### 1. ...`）なのに表が無い | その節に表を足す。番号なし見出し（`### 試験の概要` 等）は対象外 |
| `glossary-no-separator`（warn） | 用語定義の行に区切り（`…`や`:`）が無い | `* **用語** … 説明` の形にする |
| `glossary-empty-term-or-desc`（warn） | 用語名か説明が空 | 両方とも書く |
| `glossary-key-too-short`（warn） | 用語名が1文字（プレースホルダの `◯◯` 等を除いた実質1文字含む） | 2文字以上にする。1文字の用語はアプリの仕様上サポートされない |
| `glossary-duplicate-key`（info） | 同じ用語名が2回以上定義されている | 先に書いた方だけが使われる。元の項目に元々ある重複なら無視してよい |
| `materials-no-separator` / `materials-empty-name-or-desc`（warn） | 配布物版の同上 | 用語定義と同じ形に直す |
| `materials-duplicate-key`（info） | 配布物名の重複 | 同上 |
| `material-no-url`（info） | 配布物の説明に http(s) URL が無い | 元の項目にURLがあるなら反映する。無ければそのままでよい |
| `list-interrupted`（warn） | 箇条書きの途中に地の文や空行が挟まり、以降の項目が読み取られていない疑い | 箇条書きの項目同士の間に地の文を挟まない。空行なしで `*`/`-` を連続させる |
| `keyword-in-table-section`（warn） | `用語定義:`/`配布物:` の行が、表のある節（`### 1. ...` 等）の中に書かれている | 用語定義・配布物は表の無い前置きの節（`### 試験の概要` 等）に書く |
| `table-column-count-mismatch`（warn） | データ行のセル数が表の見出し行と合わない | セルの中に `\|` が紛れていないか確認する（全角の `｜` に置き換える） |
| `duplicate-item-number`（info） | 同じ項目番号が2回以上使われている | 番号を文書全体で連番に振り直す |

## このアプリの書式で特に踏み外しやすい点

- 用語名・配布物名は **2文字以上**必須（1文字だと黙って無視される。配布物名は
  例外的に1文字でも項目としては残るが、本文中のハイライト対象からは外れる）。
- 同じ用語名を2回定義すると、**後の定義は無視され、先勝ちになる**。
- `用語定義:`/`配布物:` の直後の箇条書きは、**空行や地の文で一度途切れると
  そこで読み取りが止まり**、それ以降の項目は復活しない。
- `用語定義:`/`配布物:` は、表のある節（`### 1. ...`）の中に書いても読み取られない。
  必ず表の無い前置きの節に書くこと。
- 節見出しの `【...】`/`[...]` タグは行末になければならない。
  `### See [docs](url)` のように途中や URL 由来の `)` で終わる場合はタグとして
  拾われない。

## 参考

- 書式の正本は `format.ja.md` / `format.en.md`（Test Runner アプリ内の
  `AI_FORMAT_PROMPT` と同一内容）。
- `parser.js` は Test Runner アプリ本体（`src/api/test_runner/static/js/core/parser.js`）
  から `/TestRunner/skill.zip` の生成時に直接詰められたもの。パーサーの挙動そのものは
  アプリ本体と完全に一致する（このスキル用に別ロジックを実装しているわけではない）。
